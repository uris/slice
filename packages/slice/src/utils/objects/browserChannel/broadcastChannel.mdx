        # BrowserChannel Class
        Typed wrapper around the browser `BroadcastChannel` API. It supports:
        - a typed `post` method for sending messages to every other same-origin context on the channel
        - every instance getting a unique `origin` identifier, sent with every message so receivers can tell which instance a message came from
        - a single `onMessageCallback` for every incoming message - both real `message` events and, since `messageerror` events are also forwarded to it as a synthesized `{ content, type: MessageType.Error, origin }` message, deserialization failures too - so a consumer who only wires one callback still sees everything
        - a separate `onErrorCallback`, still called with the raw `MessageEvent` on `messageerror`, for callers who want the untouched event alongside the unified stream
        - `close()` to tear down the channel and remove its listeners in one call

        ## Import
        <RenderSource>
```
import { BrowserChannel, MessageType } from '@apple-pie/slice/utils/objects';
import type { BrowserChannelMessage, ChannelConfig } from '@apple-pie/slice/utils/objects';
```
</RenderSource>

        ## Messages: data and errors
        Every message delivered to `onMessageCallback` - whether it came from a real `message` event or was synthesized from a `messageerror` event - shares one envelope shape:
        <RenderSource>
```
type BrowserChannelMessage<T> = {
	content: T | string;
	type: MessageType; // MessageType.Data | MessageType.Error
	origin: string;
};
```
</RenderSource>

        For a `MessageType.Data` message, `content` is `T` - whatever payload was passed to `post()`. For a `MessageType.Error` message, `content` is a JSON string: since a `MessageEvent`'s properties (`type`, `origin`, `lastEventId`, `data`) are getters on the prototype rather than own-enumerable fields, `BrowserChannel` reads them explicitly and serializes the result, so `JSON.parse(message.content)` gives you something to actually diagnose rather than `"{}"`.

        Check `message.type` to tell the two apart:
        <RenderSource>
```
onMessageCallback: (message) => {
	if (message.type === MessageType.Error) {
		console.error('deserialization failed:', JSON.parse(message.content as string));
		return;
	}
	console.log(message.content); // typed as T here
},
```
</RenderSource>

        ## Origin
        Every `BrowserChannel` instance gets a unique `origin` identifier, generated when it's constructed and exposed as `channel.origin`. `post()` attaches it to every outgoing message, so a receiver's `onMessageCallback` can tell which instance sent a given message - useful once more than one sender shares a channel name, since `BroadcastChannel` alone gives you no way to distinguish them.

        `origin` is always unique per instance, even between two instances created with the same `name` or the same `origin` label. It always has the shape `<label>.<uuid>` - the label is joined with a generated UUID by a dot, which is present even when no label is given - so `origin.split('.')` reliably gives you `[label, uuid]` in every case:

        ## Basic usage
        <RenderSource>
```
type ChatMessage = {
	id: string;
	text: string;
};

const channel = new BrowserChannel<ChatMessage>({
	name: 'chat',
	origin: 'tab-1',
	onMessageCallback: (message) => {
		// message: { content: ChatMessage | string, type: MessageType, origin: string }
		if (message.type === MessageType.Error) {
			console.error('failed to deserialize message', JSON.parse(message.content as string));
			return;
		}
		console.log(message.content.text, 'from', message.origin);
	},
	onErrorCallback: (event) => {
		console.error('raw messageerror event', event);
	},
});

// sent to every other same-origin tab/window/worker listening on 'chat',
// wrapped as { content: { id: '1', text: 'hello' }, type: MessageType.Data, origin: channel.origin }
channel.post({ id: '1', text: 'hello' });
```
</RenderSource>

        ## Same-origin only
        `BroadcastChannel` only delivers messages between browsing contexts on the same origin (scheme, host, and port). Use it for cross-tab or cross-worker communication within your app, not for cross-origin messaging — for that, look at `window.postMessage` instead.

        ## Unsupported environments
        `BrowserChannel` throws a `TypeError` at construction time if `BroadcastChannel` is not available, such as during server-side rendering or in older browsers:

        <RenderSource>
```
// throws: "BroadcastChannel is not supported in this environment."
new BrowserChannel({
	name: 'chat',
	onMessageCallback: () => {},
	onErrorCallback: () => {},
});
```
</RenderSource>

        Guard construction with a feature check if you need to run in an environment where `BroadcastChannel` may be unavailable:
        <RenderSource>
```
if (typeof BroadcastChannel !== 'undefined') {
	const channel = new BrowserChannel({
		name: 'chat',
		onMessageCallback: (message) => console.log(message),
		onErrorCallback: (event) => console.error(event),
	});
}
```
</RenderSource>

        ## Cleanup
        Always call `close()` when you are done with the channel. This closes the underlying `BroadcastChannel` and removes its listeners.

        <RenderSource>
```
const channel = new BrowserChannel({
	name: 'chat',
	onMessageCallback: (message) => console.log(message),
	onErrorCallback: (event) => console.error(event),
});

// later
channel.close();
```
