        # BrowserChannelsStore
        Global store for managing one or more named `BrowserChannel` instances, built with Zustand. The store keeps a named registry of channels, tracks the latest message seen per channel (as well as a shared snapshot of the latest message from any channel), and exposes both reactive hooks and imperative helpers to manage channels and read messages.

        The Slice browser channel store has a narrow goal: provide a singleton global registry of `BroadcastChannel`-backed channels and the latest message observed on each of them. Storing, persisting, or accumulating message history is left to the consuming app.

        ## Adding a channel
        `addChannel(config, replace?)` creates a new `BrowserChannel` and saves it to state under `config.name`. `config` is a `BrowserChannelConfig<T>` - the same options `BrowserChannel` takes, minus `onMessageCallback` and `onErrorCallback`: the store supplies its own internally, so every incoming message (data or synthesized error alike) is recorded on state before anything else sees it.

        There's no escape hatch to supply your own callbacks here - the store's goal is to simplify. If you need full control over message handling, use the `BrowserChannel` class directly, or the underlying `BroadcastChannel` API.

        `replace` defaults to `true`: if a channel with the same name already exists, the store closes the old channel before replacing it, and clears that name's entry in `messages` - the new instance hasn't received anything yet, so `useMessage`/`getMessage` return `null` again until it does. Pass `replace: false` to skip all of that when a channel with the same name is already registered - the existing channel, its config, and its last recorded message are left completely untouched, and `addChannel` becomes a no-op.

        <RenderSource language={'tsx'}>
        ```
        import { useEffect } from 'react';
        import {
            useBrowserChannelActions,
            useIsActiveChannel,
            useMessage,
        } from '@apple-pie/slice/stores/browserChannel';
        import { MessageType } from '@apple-pie/slice/utils';

        type ChatMessage = { id: string; text: string };

        function AppChannel() {
            const { addChannel, removeChannel } = useBrowserChannelActions();
            const active = useIsActiveChannel('chat');
            const lastMessage = useMessage<ChatMessage>('chat');

            useEffect(() => {
                addChannel({ name: 'chat', origin: 'chat-tab' });
                return () => removeChannel('chat');
            }, [addChannel, removeChannel]);

            const text =
                lastMessage?.type === MessageType.Error
                    ? `error: ${lastMessage.content}`
                    : lastMessage?.content.text;

            return (
                <div>
                    active: {active ? 'yes' : 'no'} - last message: {text ?? 'waiting...'}
                </div>
            );
        }
        ```
        </RenderSource>

        Note: Slice stores are singletons, which means you can safely import `useMessage` anywhere in your app and subscribe to the latest matching message. If you plan to make channels available globally to your app, make sure to place your channel cleanup where it makes sense.

        ## Adding several channels at once
        `addChannels(configs, replace?)` accepts a list of channel configs and registers each one the same way `addChannel` does, passing the same `replace` value through to every one of them.

        <RenderSource language={'tsx'}>
        ```
        useBrowserChannelActions().addChannels([{ name: 'chat' }, { name: 'notifications' }]);

        // skip any channel that is already registered instead of replacing it
        useBrowserChannelActions().addChannels([{ name: 'chat' }, { name: 'notifications' }], false);
        ```
        </RenderSource>

        ## Removing channels
        Removing a channel always closes it first, then removes it from the store, along with its recorded entry in `messages`. Once the last channel is removed, both `channels` and `messages` reset to `null`.

        <RenderSource language={'tsx'}>
        ```
        import { browserChannelActions } from '@apple-pie/slice/stores/browserChannel';

        browserChannelActions.removeChannel('chat');

        // or close and clear every managed channel at once
        browserChannelActions.removeChannels();
        ```
        </RenderSource>

        ## Sending messages
        `post(channelName, message)` sends `message` through the named channel's underlying `BrowserChannel`, the same as calling `channel.post(message)` directly - except you never need to hold on to the channel instance to do it. Returns `false` (and sends nothing) if no channel is registered under that name; otherwise returns `true`.

        <RenderSource language={'tsx'}>
        ```
        import { browserChannelActions } from '@apple-pie/slice/stores/browserChannel';

        type ChatMessage = { id: string; text: string };

        browserChannelActions.addChannel({ name: 'chat', origin: 'chat-tab' });

        // delivered to every other same-origin BrowserChannel/BroadcastChannel
        // listening on 'chat' - wrapped as { content, type: MessageType.Data, origin }
        // exactly as calling the BrowserChannel instance's own post() would
        const sent = browserChannelActions.post<ChatMessage>('chat', { id: '1', text: 'hello' });
        ```
        </RenderSource>

        This is the point of the store: you register a channel once with `addChannel`, then send and receive through the store alone - `post` for sending, `useMessage`/`getMessage` for receiving - without ever reaching for the `BrowserChannel` instance itself. It's still there in `channels[name]` if you need it, but the store's actions are meant to cover the common case entirely.

        ## Parent and iframe messages within one tab
        Use `useParentMessage<T>(channelName, originId)` in React or `getParentMessage<T>(channelName, originId)` outside React to read data messages associated with one top-level window. Both return the full `BrowserChannelMessage<T>` envelope, or `null` when either argument is null or empty, no message exists, the latest message is an error, or its origin does not contain `originId`.

        The app supplies the relationship: create a fresh random ID once in the parent page and pass it to its same-origin iframe. Register senders with that ID as their `origin` label. Slice appends a separate UUID to each sender's label, so the shared ID identifies the window group while each channel instance still has its own origin. A second tab must generate its own ID; a fixed label or an ID shared through local storage would group those tabs together.

        <RenderSource language={'tsx'}>
        ```
        // Parent page: register before mounting the iframe.
        import { useEffect, useState } from 'react';
        import {
            browserChannelActions,
            useParentMessage,
        } from '@apple-pie/slice/stores/browserChannel';

        type EditorMessage = { action: 'saved' };

        function EditorHost() {
            const [originId] = useState(() => crypto.randomUUID());
            const [ready, setReady] = useState(false);
            const message = useParentMessage<EditorMessage>('editor', originId);

            useEffect(() => {
                browserChannelActions.addChannel({ name: 'editor', origin: originId });
                setReady(true);
                return () => { browserChannelActions.removeChannel('editor'); };
            }, [originId]);

            return (
                <>
                    <p>{message?.content?.action ?? 'Waiting for editor'}</p>
                    {ready && <iframe title="Editor" src={`/editor?parentId=${encodeURIComponent(originId)}`} />}
                </>
            );
        }
        ```
        </RenderSource>

        <RenderSource language={'ts'}>
        ```
        // Same-origin iframe: run setup once when the editor starts.
        import { browserChannelActions } from '@apple-pie/slice/stores/browserChannel';

        const parentId = new URLSearchParams(window.location.search).get('parentId');
        if (!parentId) throw new Error('Missing parent window ID');
        browserChannelActions.addChannel({ name: 'editor', origin: parentId });

        // When the user saves in this iframe:
        browserChannelActions.post('editor', { action: 'saved' });

        // On editor teardown:
        // browserChannelActions.removeChannel('editor');
        ```
        </RenderSource>

        Outside React, the parent can read `getParentMessage<EditorMessage>('editor', originId)` as a snapshot. The same helpers can also be used inside the iframe to read parent messages labeled with the shared ID. They do not inspect `window.parent` or automatically discover the frame hierarchy.

        Matching uses `message.origin.includes(originId)`, so partial labels match too. Use full random IDs rather than short labels such as `tab-1` that could also match `tab-10`. This filters received data; it does not restrict BroadcastChannel delivery or authenticate the sender.

        These helpers filter the same single latest-message slot as `useMessage` and `getMessage`. A later message from another tab or an error replaces that slot and makes the parent selector return `null`; it does not retain the previous matching message. If other tabs must not change that slot at all, use a unique channel name per top-level window as well (for example, `editor-${originId}`) and pass that name to the iframe for registration, posting, and reading.

        ## Notes: post
        `post` is the store-level counterpart to `BrowserChannel.post()`: it looks up the live channel by name and posts through it, so sending a message never requires reaching into `channels[name]` yourself. It fails soft - posting to a name nothing is registered under returns `false` instead of throwing - so callers don't need to guard with `isActiveChannel` first unless they want to react to that case explicitly.

        ## Notes: isActiveChannel
        `isActiveChannel` lives on the actions object for imperative checks (for example, guarding a call to `addChannel` in a service layer). For React components, prefer the reactive `useIsActiveChannel` hook instead, which subscribes to changes in the channel registry.

        ## Notes: origin
        Every `BrowserChannel` the store creates gets a unique `origin` identifier (see the `BrowserChannel` docs), attached to every message it posts. Pass an optional `origin` label in `config` to make that identifier more readable - the store passes it straight through to `BrowserChannel`, which joins it with a generated UUID (`'chat-tab.<uuid>'`), rather than a bare UUID.

        This is what lets `useMessage` / `getMessage` return the sender's identity alongside the payload: the stored value for each channel is the full `{ content, type, origin }` envelope, not just `content`. Use `message.origin` to tell messages from different senders on the same channel name apart - for example, ignoring a channel's own messages when multiple tabs each register a channel with the same `name`.

        ## Notes: one shared message slot per channel
        A channel's entry in `messages` is a single slot, not one for data and a separate one for errors. Whatever arrives most recently - a real message or a synthesized `messageerror` - overwrites that slot, exactly as `BrowserChannel` itself treats an error as just another message on the same `onMessageCallback` stream. Calling `useMessage('chat')` / `getMessage('chat')` with no `type` always returns whatever is in that slot right now, whichever kind it is.

        Passing a `type` doesn't add a second slot - it filters the existing one: `useMessage('chat', MessageType.Data)` returns the slot's contents only while its `type` is `MessageType.Data`, and `null` the moment an error overwrites it (and vice versa for `MessageType.Error`). If you need to know both "did an error ever happen" and "what's the latest data" independently and simultaneously, track that yourself in your component or service layer - the store deliberately keeps one shared slot per channel to stay consistent with how `BrowserChannel` delivers messages.

        ## Notes: the replace parameter
        Use `replace: false` when you want registration to be idempotent - for example, calling `addChannel` from a component that can mount more than once, or re-running setup code without tearing down an already-connected channel. With `replace: false` and a channel already registered under that name, `addChannel` does nothing: the existing `BrowserChannel` instance, the config it was created with, and its last recorded message in `messages` are all left exactly as they were.

        With the default `replace: true`, calling `addChannel` again under the same name always closes the previous channel and creates a fresh one - useful when you deliberately want to reconnect with a different `origin` label.

        ## Importing from the root `stores` package
        `useMessage` and `getMessage` are common export names shared with other Slice connection stores (for example the SSE store also exports its own `useMessage`). Importing directly from `@apple-pie/slice/stores/browserChannel` always gives you this store's `useMessage`. Importing from the combined `@apple-pie/slice/stores` barrel instead exposes them under `useBrowserChannelMessage` and `getBrowserChannelMessage` to avoid colliding with the other stores' exports of the same name.

        <RenderSource language={'tsx'}>
        ```
        // scoped import - use the short names
        import { useMessage } from '@apple-pie/slice/stores/browserChannel';

        // combined barrel import - names are prefixed to avoid collisions
        import { useBrowserChannelMessage } from '@apple-pie/slice/stores';
        ```
        </RenderSource>

        `useParentMessage` and `getParentMessage` retain the same names in both `@apple-pie/slice/stores/browserChannel` and `@apple-pie/slice/stores`.

        ## Imperative usage outside React
        <RenderSource language={'tsx'}>
        ```
        import { browserChannelActions, getMessage } from '@apple-pie/slice/stores/browserChannel';
        import { MessageType } from '@apple-pie/slice/utils';

        type UserMessage = { id: string };

        browserChannelActions.addChannel({ name: 'user', origin: 'worker' });

        export function getLatestUserMessage() {
            const message = getMessage<UserMessage>('user', MessageType.Data);
            return message?.content ?? null;
        }
        ```
