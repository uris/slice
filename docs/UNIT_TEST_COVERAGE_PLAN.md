## How coverage actually gets to these files

Worth calling out before assigning work, because it changes what "add a test" means per file:

- **Hooks, stores, and `utils/objects`/`utils/functions`** follow a colocated `*.test.ts` convention (vitest + jsdom project). That pattern works — just extend it to the files below that don't have one yet.
- **Every component's coverage comes exclusively from Storybook stories**, run under the `storybook` vitest browser project (real Chromium via Playwright). There is no `ComponentName.test.tsx` anywhere in `src/components`. A story with a `play:` function *is* the test.
- **Prefer several small `tags: ['tests']` stories over one long sequential `play:` function.** One story = one scenario, with its own fresh mount. This isn't just style — it eliminated several real, hard-to-debug failures this pass (animation-timing races, module-level Zustand state bleeding across sequential steps within one story). Full writeup: [contributor-docs/writing-tests.md](../contributor-docs/writing-tests.md).
- Both projects feed the same coverage report. A hook or store with no accompanying `.test.ts` will show as uncovered even if it's used inside a story — rendering a component doesn't exercise every branch of the store it happens to call into. Write the unit test.

## Ninth pass: fixing real-Chromium failures from the eighth pass's batch

The user ran the eighth pass's new stories through a real `npm run coverage`/Storybook run and reported eight failures across `RadioButtonList`, `Button`, and `DraggablePanel`. All were test-code bugs (wrong assumptions about real-browser behavior), not new production bugs. Fixed in `playHelpers.ts` and the affected `.stories.tsx` files:

- **`RadioButtonList`'s `DeselectToggle`** — asserted `onChange` was last called with `([], null)` on deselect. The actual source (re-checked against `RadioButtonList.tsx`) is `onChange(state ? [options[selection]] : [], state ? [selection] : [])` — the second argument on deselect is `[]`, not `null` (`null` only ever reaches `setSelected`, a separate call). A transcription error in the original test, not a source bug. Fixed the assertion.
- **`Button`'s `OutlineDestructiveHover`** — asserted the border color via `toHaveStyle({ borderColor: 'var(--feedback-warning)' })`, which checks the browser's *computed* style (CSS variables resolved to their final color), not the literal string the component sets. Switched to reading `button.style.borderColor` directly (the raw inline style), matching the pattern already used everywhere else in this codebase's `play` functions.
- **`Button`'s `DisabledInteractions`** — asserted `onToolTip` fires on `userEvent.hover(button)` even while `disabled`. Real Chromium (correctly) doesn't dispatch realistic pointer interaction to a native `disabled` button at all — `userEvent.hover` respects that and never fires the event. Switched to `fireEvent.mouseEnter(button)` (direct dispatch, same technique already used for `TextField`'s `DisabledFieldGuards` and `UploadArea`'s busy guards), which does still reach the React handler and correctly proves `handleMouseEnter`'s tooltip call isn't itself gated by `disabled` (only `setBtnState('hover')` is).
- **`DraggablePanel`'s `TouchInteraction`** — `fireEvent.touchStart(handle, { touches: [{ clientX }] })` threw `Failed to construct 'TouchEvent'` in real Chromium; unlike jsdom, the real `TouchEvent` constructor requires actual `Touch` instances in its `touches` list, not plain objects. Added a `makeTouch()` helper using `new Touch({...})`.
- **`DraggablePanel`'s `LeftDragDirection`** — the border-settling wait used `expect(panel.style.borderLeft).not.toBe('none')`, which trivially (and wrongly) passes on the unset `''` value too, so the wait resolved before the `closed`-driven style actually settled and the very next `borderRight` assertion caught the still-unsettled state. Fixed the wait to check the handle's own `display: 'flex'` (the same open/closed signal used elsewhere) before asserting either border value.
- **`DraggablePanel`'s `ConstraintBoundaries`** — the modest, in-bounds drag (expected `300px`) came back unchanged at `250px`. Chaining three separate mousedown/mousemove/mouseup drag sessions inside one `play` function turned out to be the likely cause (each `initDrag`/`stopDrag` pair attaches/detaches document-level listeners via closures that can go stale across repeated cycles within a single mount). Split into three independent stories — `BlocksExcessiveGrowth`, `AllowsWithinBounds`, `BlocksExcessiveShrink` — each with its own fresh mount and exactly one drag, mirroring the already-proven single-drag pattern from `InitiallyClosed`.
- **`DraggablePanel`'s `VisualVariants`** — the custom three-panel side-by-side layout never reported `closed: false` at all (the `dragHandle=false` assertion's settling `waitFor` simply never resolved). Most likely cause: three 300px-wide columns inside an un-heighted flex row don't give each panel's `ResizeObserver` a stable box the way the already-proven full-viewport `DraggablePanelWithChildren` wrapper does. Replaced with four independent stories (`NoHandleAffordance`, `ContextMenuBlocked`, `ContextMenuAllowed`, `CustomBackgroundColor`), each reusing that proven single-panel wrapper (a small custom `DraggablePanelWithCustomColor` variant for the last one, since the proven wrapper hardcodes its own `backgroundColor` and would otherwise silently override the prop being tested).

None of these required touching component source — all eight were test-code fixes. `tsc`/`biome`/`vitest --project=unit` all still pass. **Still not confirmed against a real `npm run coverage`/Storybook run** — these fixes are reasoned through carefully but unexecuted by me, so a second round of failures (especially anything else in `DraggablePanel`, still the highest-risk file in this batch) wouldn't be surprising.

## Tenth pass: fixing a second round of real-Chromium failures

The ninth pass's fixes were "reasoned through carefully but unexecuted by me" — and two of its three DraggablePanel fixes turned out to be incomplete when actually run against real Chromium. A second failure report came back with three still/newly-failing tests:

- **`Button`'s `DisabledInteractions`** — `fireEvent.mouseEnter(button)` (the ninth pass's fix) still didn't trigger `onToolTip`. Root cause: React only listens for the *bubbling* native `mouseover`/`mouseout` events at the root to synthesize its `onMouseEnter`/`onMouseLeave` props — `mouseenter` itself doesn't bubble, so a raw `fireEvent.mouseEnter` dispatch never reaches React's delegated listener at all, even though it reaches a real `addEventListener('mouseenter', ...)`. Switched to `fireEvent.mouseOver(button)`, which does bubble and does reach it.
- **`DraggablePanel`'s `LeftDragDirection`** — even after confirming `handle.style.display === 'flex'` (the ninth pass's fix), `panel.style.borderRight` still read back as `''` instead of `'none'`. ## Twelfth pass: `AllowsWithinBounds` — found and fixed the real bug

The eleventh pass's `onResize` call-count signal was independent of layout, so its result was trustworthy: `expected 1 to be greater than 1` meant `canDrag` genuinely rejected the "modest, in-bounds" drag - not a test-measurement artifact. That's a real finding, not a test-code problem, which matches what was suspected.

Root cause, traced end to end: `canDrag`'s `newWidth` comes from `getNewWidth`, which starts from `startWidth.current` - and `startWidth.current` is read via `getComputedStyle(el).width` at mousedown (`initDrag`), **not** the inline `style.width`. `DrggablePanel.tsx`'s root `<div>` never set `flexShrink` (or any `flex-*` property) of its own, so as a plain child of the story's `<FlexDiv direction="row">` it fell back to the browser's default flex-item behavior: `flex-shrink: 1` with an automatic `min-width`. Because this story's panel has no real children (`children: undefined` in `meta.args`), its intrinsic content size is effectively zero, so there's nothing to stop the browser from shrinking the *actual rendered box* far below the specified `width` whenever the row is under any space pressure - even though the inline `style.width` attribute still faithfully read back `'250px'` the whole time (inline style reflects what was *specified*, not what actually rendered). That's why every earlier attempt this session saw a different symptom depending on what it measured: `style.width` (unchanged, since the assignment target never actually got exercised meaningfully), `offsetWidth` (a tiny, nonsensical value even at the settled baseline), and now the `onResize` call count (accurately reporting the drag was rejected) - because the drag's own `startWidth.current` was computed from that same tiny, collapsed real width, making `getNewWidth`'s result nowhere near the intended `[150, 400]` range.

This is a genuine, independent-of-testing product bug: a component that tracks and enforces explicit `sizeConstraints.min`/`max` should not have its actual rendered size silently violate that floor because of ordinary flexbox shrinking in a plain row layout - any real consumer embedding this panel in a space-constrained flex row (a very normal use case for a resizable side panel) would hit the same silent collapse. Fixed by adding `flexShrink: 0` to the panel's own inline style in `DrggablePanel.tsx`, with a comment explaining why. This is the first *component-source* change across all three real-Chromium fix-up rounds this pass (the ninth/tenth/eleventh passes' fixes were all test-code only).

With the root cause addressed, restored a concrete, meaningful assertion alongside the call-count check: `runDraggablePanelAllowsWithinBoundsPlay` now asserts both that `onResize` fires the 3rd (doDrag) time and that `panel.style.width` becomes the expected `'300px'`, rather than relying solely on the layout-independent proxy.

`tsc --noEmit`, `biome check --write`, and `vitest run --project=unit` (510 tests, unaffected since this is Storybook-only) all pass. **Still not confirmed against a real `npm run coverage`/Storybook run** - if this fails again, it would mean either the diagnosis is incomplete or `flexShrink: 0` alone isn't sufficient (e.g. if `min-width` needs an explicit reset too, which `flex-shrink: 0` alone does not require but is worth trying next if so). Given how well every piece of prior evidence now lines up with this explanation, this is the most confident fix of the whole DraggablePanel saga - but is still unexecuted by me.

## Fourteenth pass: `AllowsWithinBounds` - the actual root cause

The thirteenth pass's "fix" (reading the real starting width dynamically) never even ran: a follow-up automated run went back to the earlier "onResize called once" failure, and expanded console instrumentation showed the panel rendering at `2.8125px` real computed width - matching the very first, months-old "~3px" observation from long before the `flexShrink: 0` fix existed, proving that fix had had zero effect on the actual failure the whole time.

The user's own hunch nailed it: this is about the panel's mount/open animation, not layout collapse. Traced precisely: `DrggablePanel.tsx` has `const [mounted, setMounted] = useState(false)` plus `useEffect(() => setMounted(true), [])`, and `normalizeWidth` returns `'0px'` whenever `!mounted`. That means **every** mount of this component renders at width `0` for at least the first paint, regardless of `isClosed`, and only jumps to its real target width once the mount effect flips `mounted` to `true` on a subsequent render. Since `isDragging` is `false` at that point, the CSS `transition` on the panel's `width` (`--motion-water-duration: 0.25s`, confirmed in `src/theme/motion/motion.css`) is active - so the panel doesn't snap to its target width, it *animates* to it over 250ms.

`waitForConstraintPanelReady` was only waiting for the inline `style.width` attribute to say `'250px'`, which updates instantly the moment React decides on the target - it says nothing about whether the 250ms CSS animation towards that target has actually finished. `startWidth.current` (what all the drag math is based on) is read via `getComputedStyle`, which reflects the real, still-animating rendered value, not the inline target. So every previous round's drag started from an essentially arbitrary point along that 250ms curve depending on pure timing luck: ~2.8px when the automated headless runner reached it within a few milliseconds of mount, ~196px or ~673px when a slower, human-paced manual interaction gave the transition more real time to progress. This explains every single reading from every round of this saga with one mechanism - none of the earlier diagnoses (container-width timing, flex-shrink collapse, the `canDrag` boundary condition) were wrong to fix, they just weren't what was making this specific test flaky.

Fixed `waitForConstraintPanelReady` to wait for the actual computed width to catch up to the specified inline width (bounded `waitFor` at 1000ms, comfortably past the 250ms transition) before any drag starts. Removed all temporary debug instrumentation from `DrggablePanel.tsx` (`canDrag` and `initDrag` are back to their pre-debugging state, with the `flexShrink: 0` and strict `</>` boundary-check fixes from the twelfth pass both kept - real, independent improvements even though neither was this bug).

`tsc --noEmit`, `biome check --write`, and `vitest run --project=unit` (510 tests) all pass. This is the highest-confidence fix in the entire `DraggablePanel` saga: it's the first one with an actual, traceable mechanism (a named `useState`/`useEffect` pair plus a real, measured CSS custom property) rather than an inference from indirect symptoms, and it explains every prior reading rather than just the latest one.

**Two real production bugs found and fixed**, both in `IndexedDB.tsx`, both invisible without a spec-accurate fake (nothing in this codebase had exercised real `IndexedDB` semantics before - the class had zero prior test coverage):

## How this was built

Generated from the coverage run checked in under `reports/coverage/coverage-final.json` (produced by `npm run coverage`, v8 provider) — not a manual code walk, same methodology as the original pass. Per-file statement/function/branch percentages were computed directly from that file's `s`/`f`/`b` maps (v8's coverage format doesn't have Istanbul's separate "lines" metric, so statement % is used as the closest proxy). Files under 3 statements (barrel `index.ts` re-exports, type-only `_types.ts` files) and generated `*.figma.ts` manifests (gitignored, exploratory) were excluded as noise. `LocalDB`, `WebRTC` (store + hook), `WebRTCConnection`, and `IndexedDB` were excluded per the same explicit scope decision as the original pass. Each Tier 0/1 file's `play`-function status was re-checked against its actual `.stories.tsx` source (`grep -c 'play:'`), not inferred from the coverage numbers alone.

This is the second revision of this document. The first revision (which itself superseded the "3. Unit Tests — path to ~80% coverage" section of `docs/PUNCH_LIST.md`) drove the work summarized in "Progress since baseline" above — the isolated-`tags: ['tests']`-story pattern, the Zustand-reset convention, and the two real bugs found along the way (`Modal.tsx`'s missing `aria-label`, `DataTable.tsx`'s unmemoized `elements` object) are all now written up in [contributor-docs/writing-tests.md](../contributor-docs/writing-tests.md) so they don't have to be rediscovered.
