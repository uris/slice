        # useClipboard
        Reads from and writes to the system clipboard, observes native `paste` events, and reports live `clipboard-read`/`clipboard-write` permission state. Upgrades the write-only `copyToClipboard` util into a full hook: `copy()` still falls back to the legacy `execCommand` approach when the async Clipboard API is unavailable or denied.

        ## Behavior
        `copy()` prefers `navigator.clipboard.writeText()` and transparently falls back to a hidden-textarea `execCommand('copy')` when the Clipboard API is missing or the write is rejected (e.g. an insecure context, or a browser that requires a permission the user hasn't granted). `read()` requires the async Clipboard API and, in most browsers, a user gesture or granted `clipboard-read` permission — it resolves to `null` rather than throwing when unsupported or denied.

        Separately, the hook always listens for native `paste` events on `target` (a ref, an element, or `document` by default) so consumers get pasted text and files without needing clipboard-read permission at all — this is the same mechanism the browser already uses for paste-into-input behavior, just observed rather than requiring an explicit read.

        Permission state is queried once on mount via the Permissions API (`clipboard-read` and `clipboard-write`) and kept live via `PermissionStatus`'s `change` event, when the browser supports it. Firefox and other browsers without Permissions API support for these names report `unsupported` rather than throwing.

        ## Signature
        `useClipboard(options?)`

        ## Notes
        - `copy()` never throws — a failed write (from both the Clipboard API and the fallback) surfaces through `error` and a `false` return value instead.
        - `read()` and the live `readPermission`/`writePermission` values depend on the Permissions API supporting the `clipboard-read`/`clipboard-write` names, which is not universal (notably Firefox). Both report `unsupported` rather than misrepresenting state.
        - Listening for `paste` does not call `preventDefault()`, so default paste behavior (e.g. into a focused native input) keeps working alongside `onPaste`.
        - `target` defaults to `document`, so a bare `useClipboard()` call observes paste anywhere on the page. Pass a ref to scope it to one drop zone or editor.
        - **Safari caveat:** WebKit only dispatches `paste` when the cursor sits inside an editable context (a focused `<input>`/`<textarea>`, a `contentEditable` element) or there's an active text selection — clicking a plain, non-editable element doesn't create that context, so ⌘V silently does nothing there. Chrome and Firefox are more lenient and will still dispatch `paste` in that case. If `target` is a custom container rather than a real form control, make it `contentEditable` (see the scoped example below) so Safari has somewhere to place the cursor.

        ## Basic example
        </Unstyled>

        <RenderSource language={"tsx"}>
        ```
        import { useClipboard } from '@apple-pie/slice';

        function CopyButton() {
            const { copy, isCopied, error } = useClipboard();

            return (
                <div>
                    <button type="button" onClick={() => copy('Hello from Slice')}>
                        {isCopied ? 'Copied!' : 'Copy'}
                    </button>
                    {error ? <span>{error.message}</span> : null}
                </div>
            );
        }
        ```

        ## Scoped paste example

        <RenderSource language={"tsx"}>
        ```
        import { useRef } from 'react';
        import { useClipboard } from '@apple-pie/slice';

        function PasteZone() {
            const zoneRef = useRef<HTMLDivElement>(null);
            const { readPermission } = useClipboard({
                target: zoneRef,
                onPaste: (result) => console.log(result.text, result.files),
            });

            // contentEditable gives the browser somewhere to place the cursor. Without it,
            // Safari never dispatches `paste` here — clicking a plain div isn't an editable context.
            return (
                <div ref={zoneRef} contentEditable suppressContentEditableWarning>
                    Paste here (read permission: {readPermission})
                </div>
            );
        }
        ```
