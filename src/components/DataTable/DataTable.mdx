        # DataTable
        `DataTable` renders a scrollable, typed table bound to an array of row data. Columns are declared separately from the row shape, each reading its value via a `key` or an accessor and carrying optional custom header/cell renderers, so the table's markup stays generic while every column stays fully typed.

        ## Base element
        `HTMLDivElement` (scroll wrapper) containing an `HTMLTableElement`.

        ## Typing
        `DataTable` is generic over `T`, the shape of a single row. Specify it explicitly so `columnDefinitions` and `tableData` are checked against your row type.

        ## Building columns
        Most columns just read a field straight off the row - give those a `key` and the cell's value comes out typed as `T[K]`, no helper needed:

        <RenderSource>
        ```
        const columns: ColumnDefinition<Person>[] = [
            {
                id: 'age',
                key: 'age',
                title: 'Age',
                align: 'end',
                renderCell: ({ value }) => <span>{value} yrs</span>, // value: number
            },
        ];
        ```
        </RenderSource>

        When a column's value has to be computed instead - combining fields, formatting, deriving something that isn't just sitting on the row - build it with `createColumnHelper<T>()`. It infers the value type from whatever the `accessor` function returns, so `renderCell`/`renderHeader` still get a typed `value`:

        <RenderSource>
        ```
        const column = createColumnHelper<Person>();

        const columns = [
            column.accessor(row => `${row.firstName} ${row.lastName}`, {
                id: 'name',
                title: 'Full Name',
                renderCell: ({ value }) => <span>{value}</span>, // value: string
            }),
        ];
        ```
        </RenderSource>

        `key` and `accessor` are mutually exclusive on a column. A column can also carry neither - useful for a purely presentational column, like row actions, where `renderCell` doesn't need a row-derived value at all.

        ## Cell fallbacks
        Because `renderCell` gets `row` as well as `value`, a column can fall back to a different field without reshaping the accessor's return type:

        <RenderSource>
        ```
        column.accessor(row => row.pic, {
            id: 'photo',
            title: 'Profile Photo',
            renderCell: ({ value, row }) =>
                value ? <Avatar image={value} name={row.name} /> : <Avatar name={row.name} />,
        })
        ```
        </RenderSource>

        If a resolved display value needs to exist independent of rendering (for CSV export, search, or sort, where there's no `row` around to fall back to), push the fallback into the accessor instead and return something that still distinguishes the cases, such as a small discriminated union (`{ kind: 'image'; url: string } | { kind: 'initials'; label: string }`), rather than collapsing both cases into one plain string.

        ## Filtering rows
        `filter` narrows `tableData` before it's rendered, using the exact signature of `Array.prototype.filter`, so an existing predicate - including a type-narrowing one - can be passed straight through without adapting it:

        <RenderSource>
        ```
        const filter = (row: Person) => row.country !== '';

        <DataTable<Person> columnDefinitions={columns} tableData={people} filter={filter} />
        ```
        </RenderSource>

        `DataTable` doesn't manage filter state itself - `filter` is a plain predicate prop, so building a search box or a set of toggles on top of it is just component state feeding a new predicate in on every render. Because filtering happens before rendering, `rowIndex` everywhere downstream (`getRowId`, `onClick`/`onDoubleClick`/`onMouseOver`/`onMouseOut`, and `renderCell`'s `CellContext`) reflects the row's position in the filtered rows, not the original `tableData` array.

        ## Sorting
        Give a column a `sort` field - the row key to sort by - and its header becomes clickable: click once to sort ascending, click again to flip to descending, click a different sortable header to switch to that column instead. Only one column is sorted at a time.

        <RenderSource>
        ```
        column.accessor(row => row.age, {
            id: 'age',
            title: 'Age',
            align: 'end',
            sort: 'age',
            renderCell: ({ value }) => <span>{value} yrs</span>,
        })
        ```
        </RenderSource>

        The default header renderer shows a small up/down arrow next to the title of whichever column is currently sorted, and reserves that same space (rather than shifting the title around) on every other sortable column. A custom `renderHeader` gets the same information through `sortKey` on its context, so it can draw its own indicator instead:

        <RenderSource>
        ```
        renderHeader: ({ column, sortKey }) => {
            const sorted = sortKey?.key === column.sort;
            return (
                <div style={{ display: 'flex', justifyContent: 'space-between', width: '100%' }}>
                    <span>{column.title}</span>
                    <Icon name={sorted ? (sortKey.dir === 'asc' ? 'arrow up' : 'arrow down') : 'blank'} size={16} />
                </div>
            );
        }
        ```
        </RenderSource>

        `sort` is optional on `DataTable` itself, and works two ways:

        - Omit it and `DataTable` manages sort internally - clicking a header just works, with no state to wire up. This is enough for most tables.
        - Pass it alongside `onSortChange` to run sort as a controlled value: clicking a header calls `onSortChange` with the next `SortKey<T>` instead of relying only on internal state, and it's on you to feed that value back in through `sort` - useful for driving sort from elsewhere in the app, or for persisting it (see <a href="#persisting-column-layout">Persisting column layout</a>).

        Every sortable header is also a real keyboard target (Enter/Space activates it, matching a click) and carries the right `aria-sort` (`ascending`, `descending`, or `none`), so sorting doesn't depend on a mouse.

        ## Row hover and click events
        `onClick`, `onDoubleClick`, `onMouseOver`, and `onMouseOut` all fire per body cell with the same arguments - the cell's `ColumnDefinition`, its column index, the row, and the row's index - so a single handler can branch on `col.id` when it needs to know which column was involved:

        <RenderSource>
        ```
        <DataTable<Person>
            columnDefinitions={columns}
            tableData={people}
            onClick={(col, colId, row, rowIndex) => {
                if (col.id === 'name') selectPerson(row);
            }}
        />
        ```
        </RenderSource>

        Hovering (or focusing, via keyboard) a cell also drives the row's background: `backgroundColorHoverRow` is applied to every cell in that row for as long as it's hovered, taking priority over `candyStripeBackgroundColor`'s alternating stripe. This is purely visual state internal to `DataTable` - `onMouseOver`/`onMouseOut` are how a consumer observes it, not how it's controlled.

        ## Resizing columns
        Every column except the last gets a draggable edge on its right side, on by default. Drag it to resize that column; hovering (or focusing) the edge shows a vertical line as a preview before you commit to a drag. Set `colResize={false}` to turn this off entirely.

        <RenderSource>
        ```
        <DataTable<Person> columnDefinitions={columns} tableData={people} colResize={false} />
        ```
        </RenderSource>

        A resized width is kept internally for as long as `DataTable` stays mounted, so it survives sorting, filtering, and re-renders without any extra wiring. It does *not* survive on its own past a remount, a page reload, or the table being given a fresh `columnDefinitions` array from a saved `DataTableViewState` - for that, listen for `onColumnResize` and fold the result into your own state, the same way `onSortChange` works for sort. See the next section for how that fits into `DataTableViewState`.

        ## Reordering columns
        Drag a column's header to move it. Columns shift live the moment the dragged header crosses into another column's space - there's no need to wait for a drop - and the column being dragged renders at reduced opacity for the duration, since its position isn't committed yet. Dropping anywhere on the header row commits the move; dropping outside the header row, or on the frozen column when `freezeColumn` is set, cancels the whole drag and every column snaps back to where it started.

        <RenderSource>
        ```
        <DataTable<Person>
            columnDefinitions={columns}
            tableData={people}
            onColumnReorder={(columnOrder) => console.log(columnOrder)}
        />
        ```
        </RenderSource>

        The frozen column (when `freezeColumn` is set) can't be dragged, and nothing can be dropped into its slot - it stays pinned at the start of the table through any reorder.

        There's no prop to turn reordering off - unlike resizing, it's always available. Reordering and resizing don't interfere with each other: dragging a header moves the column, while dragging its right edge (see <a href="#resizing-columns">Resizing columns</a> above) resizes it. Reordering is currently drag-only - there's no keyboard equivalent, unlike sorting's Enter/Space activation.

        Like a resized width, a reordered layout is kept internally for as long as `DataTable` stays mounted, and does *not* survive on its own past a remount or reload - listen for `onColumnReorder` and fold the result into your own state, the same way `onColumnResize` works for width. Unlike `onColumnResize`, which fires once when a resize drag ends, `onColumnReorder` fires throughout a live drag - once per column boundary crossed - so it always reflects the order currently on screen, right through a cancelled drag reverting back to where the columns started. See the next section for how that fits into `DataTableViewState`.

        ## Persisting column layout
        `columnDefinitions` always carries functions (`accessor`, `renderHeader`, `renderCell`), so it can't be saved as-is. What actually needs to survive a reload or sync to a backend is much smaller: which columns are visible, what order they're in, how wide they are, and which one is sorted. `DataTableViewState` is that smaller, plain-data shape, referencing columns purely by `id`:

        <RenderSource>
        ```
        type DataTableViewState = {
            columnOrder: string[];
            hiddenColumns?: string[];
            columnWidths?: Record<string, number | string>;
            sort?: { columnId: string; dir: 'asc' | 'desc' };
        };
        ```
        </RenderSource>

        A live resize is captured the same way a live sort change is: `onColumnResize(columnId, width)` fires whenever a drag ends, and you fold that into `columnWidths` yourself - there's no `captureColumnWidthsToViewState` helper, since the merge is just one key:

        <RenderSource>
        ```
        <DataTable<Person>
            columnDefinitions={applyDataTableViewState(columns, viewState)}
            tableData={people}
            onColumnResize={(columnId, width) =>
                setViewState(prev => ({
                    ...prev,
                    columnWidths: { ...prev.columnWidths, [columnId]: width },
                }))
            }
        />
        ```
        </RenderSource>

        A live reorder is captured the same way: `onColumnReorder(columnOrder)` fires with the full column id order, and you write that straight into `columnOrder` - no merging needed, since it's the whole array, not a per-column patch like `columnWidths`:

        <RenderSource>
        ```
        <DataTable<Person>
            columnDefinitions={applyDataTableViewState(columns, viewState)}
            tableData={people}
            onColumnReorder={(columnOrder) =>
                setViewState(prev => ({ ...prev, columnOrder }))
            }
        />
        ```
        </RenderSource>

        `applyDataTableViewState(columns, state)` reconciles a code-defined `columnDefinitions` array against a persisted `DataTableViewState`: it reorders to match `columnOrder`, drops `hiddenColumns`, applies `columnWidths`, appends any columns the state doesn't mention (for example a column added in code after the state was captured), and silently ignores ids in `columnOrder` that no longer exist (a deleted or renamed column) rather than breaking the table. It's a standalone function, not a `DataTable` prop - call it wherever `columnDefinitions` is assembled, before it reaches `DataTable`. `createDefaultViewState(columns)` gives you a starting `DataTableViewState` that reflects the columns' natural order, for when nothing's been saved yet.

        `sort` on `DataTableViewState` references the sorted column by `id`, the same way `columnOrder` does, rather than by the row key it sorts on - that way a saved sort survives a column's `sort` field or accessor changing in code, as long as its `id` doesn't. Since `DataTable`'s own `sort` prop needs the actual row key (a `SortKey<T>`, not a column id), two helpers convert between the two shapes: `resolveSortFromViewState(columns, state)` turns a saved `DataTableViewState` into the `SortKey<T>` that `DataTable`'s `sort` prop expects, resolving to `undefined` - rather than throwing - if there's no saved sort, or the referenced column is gone or no longer marked sortable in code. `captureSortToViewState(columns, sort)` does the reverse: given the `SortKey<T>` from `onSortChange`, it finds the matching column and returns the `{ columnId, dir }` shape to write back into your view state. The second example below wires all four pieces together.

        ## Code examples
        </Unstyled>

        <RenderSource>
        ```
        import { DataTable, createColumnHelper } from '@apple-pie/slice';

        type Person = {
            name: string;
            age: number;
            pic: string;
            country: string;
            compensation: number;
        };

        const column = createColumnHelper<Person>();

        const columns = [
            column.accessor(row => row.name, { id: 'name', title: 'Full Name' }),
            column.accessor(row => row.age, {
                id: 'age',
                title: 'Age',
                align: 'end',
                sort: 'age',
                renderCell: ({ value }) => <span>{value} yrs</span>,
            }),
            column.accessor(row => row.compensation, {
                id: 'salary',
                title: 'Salary',
                align: 'end',
                sort: 'compensation',
                renderCell: ({ value }) => <span>${value.toLocaleString()}</span>,
            }),
        ];

        const people: Person[] = [
            { name: 'John Appleseed', age: 25, pic: '', country: 'Portugal', compensation: 1_000_000 },
        ];

        export function PeopleTableExample() {
            return (
                <DataTable<Person>
                    columnDefinitions={columns}
                    tableData={people}
                    getRowId={row => row.name}
                    id="people-table-example"
                    data-testid="people-table-example"
                />
            );
        }
        ```
        </RenderSource>

        <RenderSource>
        ```
        import { useState } from 'react';
        import {
            DataTable,
            applyDataTableViewState,
            resolveSortFromViewState,
            captureSortToViewState,
            type DataTableViewState,
        } from '@apple-pie/slice';

        // as if just read back from localStorage or a backend
        const savedViewState: DataTableViewState = {
            columnOrder: ['salary', 'name'],
            hiddenColumns: ['age'],
            columnWidths: { salary: '30%' },
            sort: { columnId: 'salary', dir: 'desc' },
        };

        export function PeopleTableWithSavedLayoutExample() {
            const [viewState, setViewState] = useState(savedViewState);

            return (
                <DataTable<Person>
                    columnDefinitions={applyDataTableViewState(columns, viewState)}
                    tableData={people}
                    getRowId={row => row.name}
                    sort={resolveSortFromViewState(columns, viewState)}
                    onSortChange={sort =>
                        setViewState(prev => ({ ...prev, sort: captureSortToViewState(columns, sort) }))
                    }
                    onColumnResize={(columnId, width) =>
                        setViewState(prev => ({
                            ...prev,
                            columnWidths: { ...prev.columnWidths, [columnId]: width },
                        }))
                    }
        ```
